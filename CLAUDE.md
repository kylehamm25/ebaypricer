# CLAUDE.md

## What this is

An automated eBay selling pipeline for a Pokemon card business, plus a dashboard to view the data. Two halves that share a database but run independently:

1. **Pipeline** (`src/ebaypricer/` + `scripts/`) — Python scripts that talk to eBay's Trading/Browse/Marketing/Finances APIs, do pricing research, and read/write an Excel workbook (`H:\My Drive\ebay\ebay_sold_orders.xlsx`, path in `EBAY_EXCEL_PATH`) as the bookkeeping source of truth. Runs hourly via Windows Task Scheduler (`scripts/run_hourly.ps1`).
2. **Dashboard** (`dashboard/backend` FastAPI + `dashboard/frontend` React/Vite) — reads from Postgres/Supabase, displaying sold orders, active listings, and pricing. On startup it syncs the Excel workbook into Postgres (`services/excel_sync.py`).

The project is mid-migration from a single-user local SQLite tool to a multi-user Supabase-backed SaaS. **Read `docs/SOFTWARE_PLAN.md` before touching schema, auth, or the migration path** — it documents the current vs. target architecture, the full Postgres schema, and the phase plan. Treat it as living design doc, not historical record; update it when a phase completes or the plan changes.

A third piece, `ebay-defaults-extension/`, is a standalone Chrome extension (vanilla JS, no build step) for filling eBay listing form defaults — unrelated to the Python/dashboard code.

## Commands

### Pipeline (Python, from repo root)
```bash
pip install -e .                        # required: installs src/ebaypricer as editable package
python scripts/main.py                  # full pipeline, sequential, logs to logs/main.log
python scripts/gen_access_token.py      # one-time OAuth consent flow -> writes tokens to .env
python scripts/price_active_listings.py --force   # bypass daily SQLite cache
```
No test suite exists in this repo currently.

### Dashboard backend (FastAPI, from repo root)
```bash
python -m uvicorn dashboard.backend.main:app --host 127.0.0.1 --port 8000 --reload
```

Frontend commands are the standard `npm run` scripts in `dashboard/frontend/package.json`.

### Full stack shortcuts
- `start-dashboard.bat` — starts backend (:8000) and frontend dev server (:5173) in separate windows, dev mode.
- `start-prod.bat` — builds the frontend if needed, installs deps, serves everything from FastAPI on :8000 (single-host mode).
- `Dockerfile` — multi-stage build (Node for frontend, Python 3.13-slim for backend); frontend `VITE_*` build args are baked in at image build time, not runtime.

### Database migrations
`db/migrations/NNNN_*.sql` are numbered, idempotent (`create ... if not exists`), and **applied by hand** — paste into the Supabase SQL editor and run in order. There is no migration runner. Code that depends on a new table should degrade rather than crash if the migration hasn't been run yet (see `price_research.recent_price_changes`, which logs and returns empty when `price_change_log` is missing).

## Architecture

### Two pricing paths (important)

Pricing research exists **twice**, and new work belongs in the second one:

- **Legacy (Excel):** `scripts/price_active_listings.py` + `scripts/avg_active_price.py`, driven by `scripts/main.py`, using the Excel workbook and local SQLite as the inter-step data channel.
- **Current (Postgres):** `dashboard/backend/services/price_research.py` — shared, server-side, runs once per unique card **across all users** and writes the shared snapshot tables plus every user's derived `active_listings` columns. It supersedes the two scripts above.

Both still exist because the legacy path serves the single-user Excel workflow while connected users go through `services/ebay_data.py`. When changing pricing logic, change `price_research.py`; only touch the scripts if the Excel workflow specifically needs it. Shared numeric helpers live in `src/ebaypricer/listing_economics.py` (tiered fee/net estimation, `resolve_shipping_charge`) precisely so both paths agree. `resolve_shipping_charge` prefers eBay's own `ShippingServiceCost` when the Trading API returns one, falling back to the static per-profile estimate (`shipping_charge_for_profile`) for Calculated-shipping listings that don't have package weight/dimensions set — both `get_active.py` and `ebay_data.py` call it the same way.

**There is no sold-side research at all, deliberately.** The Browse API silently ignores the `soldDate` filter and returns ordinary active listings, so anything labeled "sold" from Browse is wrong. That was replaced by a TCGdex/TCGPlayer market price stored in `price_snapshots` — one current asking-price point, not a record of any sale — and that has now been removed too, because it read as sold data on every screen it reached. Gone with it: `research_card_sold`, the `price_snapshots`/`sold_listings` writes and reads, the `Recent Sold Avg` / `Price vs Sold Avg` / `Recent Sold Count` columns (and their Excel mappings), the sold series on the listing chart, and `scripts/price_active_listings.py`'s place in the legacy chain. `price_accuracy` is now measured against the comp average alone. Real sold comps would need eBay's Marketplace Insights API, which is restricted-access and not on this app's scopes; until then, don't reintroduce a Browse sold search *or* a "sold" number derived from a market-price lookup. (Sold **orders** — the `sold_orders` table behind the Sold page, lots and dashboard — are your real sales and are untouched by any of this.) Active-listing search via Browse *is* real — but its results are **not** usable as-is: Browse matches on words, not card identity, so a pool arrives mixed with graded slabs, multi-card lots, print-error one-offs, foreign/Japanese prints and wrong prints. `src/ebaypricer/comp_filter.py` screens them out before any aggregate is computed, and records what it dropped in `active_price_snapshots.pool_quality` (migration 0010). Add a new contamination rule there, not in the aggregation code. Note also that the `card_query` string is a **catalog** identity, not a search string: `browse_api._build_query` runs it through `cards.searchable_card_query` first, because the SVP promos are catalogued as `SVP13` but titled `SVP 013` — searching the catalogued form returned literally zero results. Don't change `_fmt_card`/`card_query` to fix a search problem; it keys the snapshot tables.

### Suggested price model
`dashboard/backend/services/suggested_price.py` is the single canonical pricing model, and it is **pure** — no DB, no network, no clock; callers pass clock-derived inputs in rather than letting the module read the time. Two prohibitions that outlive any detail: **don't reintroduce pricing math in the frontend** (a client-side `computeRecommendedPrice` used to produce different numbers on the list page vs. the detail page), and don't make the module impure to get at "now".

Everything else — the anchor pipeline, each guardrail and status, which inputs feed it, and what must never be reintroduced — lives in the **`ebay-pricing-rules` skill**, which loads on demand, plus the tuning-constant comments at the top of `suggested_price.py`. Read the skill before changing pricing logic, explaining a suggested price, or adding a pricing input. It is deliberately the only prose copy of the model, so nothing here can drift out of sync with the code.

### Background jobs, locks, and status
Every long-running backend job follows one pattern: a process-local `threading.Lock` for fast rejection, a **Postgres advisory lock** for cross-process exclusion, and start/finish rows in the `job_runs` table so `/pipeline/status` and the per-page refresh buttons can report progress. Advisory-lock keys must be unique per job — currently `727001` (`pipeline_runner`), `727002` (`price_research`), `727003`/`727004` (`stage_runner` sold/active). Pick a new key for a new job.

`price_research.reconcile_stale_job_runs()` runs at startup to mark rows orphaned by a crash; this assumes single-instance deployment.

Job entry points:
- `services/pipeline_runner.py` — runs the whole legacy `scripts/main.py`, then ingests Excel + SQLite into Postgres.
- `services/stage_runner.py` — page-level refresh of just one slice (`sold_refresh`, `active_refresh`), so a page can update without a full pipeline run.
- `services/price_research.py` — `run_shared_price_research()` (whole catalog, has a 45-minute wall-clock budget), `refresh_card()` (one card, bypasses the batch lock for the per-listing Refresh button), `recompute_suggestions()` (zero eBay calls; recomputes from existing snapshots).
- `services/ebay_data.py` — per-user OAuth sync, replaces the Excel workbook for connected users; runs on a background scheduler and on demand.
- `services/promotion_boost.py` — per-user ad-rate boosting using each user's own token. **Only ever runs on a deliberate request** (`POST /ebay/promotion-boost`). The scheduled round and the pipeline's `auto_boost_promotion` step were both removed: ad rates are real, not-trivially-reversible spend, so nothing may put them back on a timer.

### Pipeline data flow (legacy)
`scripts/main.py` chains five sub-scripts over the Excel workbook. The per-script
detail lives in `scripts/CLAUDE.md`, which loads when you work in that directory.

Shared library in `src/ebaypricer/`: `auth.py` (OAuth token refresh, persisted to `.env`), `trading_api.py`, `browse_api.py`, `marketing_api.py`, `finances.py`, `cards.py` (Pokemon card DB, fuzzy matching, TCGdex market price, `card_identity()`; caches in `data/`), `comp_filter.py` (pure comp-pool screening — see above), `listing_economics.py`, `excel.py` (workbook styling), `paths.py` (all file paths — `PROJECT_ROOT`, `DB_PATH`, cache files; import from here rather than hardcoding paths).

Local SQLite lives at `db/pokemon_prices.db`. Some tables are shared marketplace data (`active_snapshots`, and the now-unwritten `price_snapshots`/`sold_listings`), rebuilt/appended incrementally; others mirror the workbook and get dropped/recreated each sync — see `docs/SOFTWARE_PLAN.md` §3 for the full schema and which tables are "shared" vs "user-owned" in the Supabase target.

### Dashboard backend
FastAPI app in `dashboard/backend/main.py`. On startup: reconciles orphaned `job_runs`, starts the per-user sync scheduler if any eBay connections exist, then syncs the Excel workbook into Postgres. Serves the built frontend (`dashboard/frontend/dist`) directly when present, with SPA fallback routing — so in single-host/prod deployment there's one process on :8000.

- `database.py` — psycopg3 connection pool (`get_db()`), defaults to read-only transactions. The pool is small (5); never take a second connection while holding one (pass data down instead — see `update_active_listing_derived_columns`).
- `config.py` — all env vars, read through `_env()` which strips surrounding quotes (needed because Docker `--env-file` keeps them). Env vars are organized by migration phase — check `.env.example` for the phase each one belongs to before adding new config.
- `auth.py` — Supabase JWT verification (`get_current_user_id`), tries ES256-via-JWKS first, falls back to legacy HS256-via-shared-secret. When `AUTH_REQUIRED` is unset, falls back to `DEFAULT_USER_ID` for local single-user dev.
- `routers/` — one file per resource (`dashboard`, `sold`, `active`, `lots`, `inventory`, `pricing`, `pipeline`, `promotion`, `ebay`, `valuation`). `active.py` is the largest: listing list/detail, per-listing and bulk price apply (which write `price_change_log` and call `trading_api.revise_item_price`), per-card refresh, price-change history (`GET /active/price-changes`), and the analytics aggregations. `pricing.py` and `promotion.py` are still mounted but no frontend page currently calls them.
- **A listing's catalog match is editable, and the correction sticks.** `active_listings.card` comes from fuzzy-matching the eBay title, which gets the right card in the wrong set, or the base print of a stamped promo — and that is not cosmetic, it prices the listing against a different card. `PUT /active/item/{id}/card` stores a chosen identity (or free-text search string) and sets `card_locked` (migration 0013); both sync paths then write `card = CASE WHEN active_listings.card_locked THEN active_listings.card ELSE EXCLUDED.card END` via `services/upsert_rules.set_clause`, which is the **only** copy of that rule — before it, every hand correction was silently undone by the next sync. Clearing the match clears the lock and hands the row back to the matcher. `upsert_rules` checks the column exists once per sync and falls back to the plain overwrite, so an un-migrated install syncs as before. Setting a match researches that one card, the same path the per-listing Refresh uses. Note `card_locked` is deliberately NOT in `active.py`'s `_SELECT` — the list endpoint shares it, and a missing column there would take the whole listings page down. `active_listings.number` (migration 0019) rides alongside `card` under the same lock — it's the card number `ebaypricer.cards.card_number()` (a thin `card_identity()` wrapper) parses out of `card`, stored purely so the Active Listings page can sort by it in SQL, since the number is embedded in `card`'s formatted string rather than a column of its own. Both sync paths derive it whenever they write `card`, `PUT /active/item/{id}/card` derives it too when a match is corrected by hand, and it's the page's **default sort** (ascending) on a fresh load. All three write sites check the column exists first rather than catching the failure after — a failed statement aborts the whole transaction, so there's no retrying a corrected query on the same connection, unlike a fresh one.
- **Applying a price changes the price and nothing else.** Best Offer auto-accept and minimum-offer thresholds are the seller's to set on the listing; repricing must not read, write, or derive them. `revise_best_offer_thresholds` and `revise_price_with_best_offer` were deleted from `trading_api.py` for this reason, along with `OFFER_THRESHOLD_PCT` in `active.py` (which pinned both to 90% of the new price) and the bulk result's `"partial"` status (price landed, thresholds didn't — no longer a reachable state). Don't reintroduce any of it. If a deliberate, separate offer-threshold action is ever wanted, note that eBay validates each side against what's currently live, so price and thresholds can never move in one `ReviseFixedPriceItem` call — the ordering rules are written up in `.claude/skills/ebay-listing-dry-run/SKILL.md`.
- `services/inventory_value.py` — what an unlisted row is worth (stated price, else cached comp average × the shared condition multiplier). The **only** copy: `routers/inventory.py` and `routers/lots.py` both call it, so a lot's unlisted total and the Inventory page can never disagree about the same cards. It never researches — callers pass a connection and get one snapshot query per page. `raise_below_minimum` is the one write in the module: called from `PUT /settings/listing-defaults` whenever a `min_price` (migration 0018) is saved, it bumps every active row already worth less than that floor up to it by setting `manual_value` — a real write, not a guardrail added to `row_value`, which stays the thin comp-times-multiplier calculation the ebay-pricing-rules skill requires. It only ever raises (a row at or above the minimum, or with no known value yet, is left alone), applies to comp-priced and already-manually-priced rows alike, and — because manual_value wins over comps — a raised row stops following its comp price and holds at the minimum until someone clears manual_value by hand.
- `routers/inventory.py` — cards owned but **not yet listed** (`inventory`, migration 0011). The one hand-entered table in the app: eBay knows nothing about a box on the desk, so nothing syncs or overwrites it, and there is still no "listed" flag — `archived_at` (migration 0014) records that a row **left the pile**, not that the card is on eBay, and nothing reconciles it against `active_listings`, which remains the only thing that knows. Archived rows drop out of every ordinary read: the list defaults to the live pile (`?archived=archived|all` to see otherwise), the totals count only what is still in it, and a lot's `unlisted_items`/`unlisted_value` ignore them — otherwise a listed card would sit in a lot's unlisted column *and* be counted again in its `listed_value`, which is the double count 0011 was guarding against. Archiving rather than deleting keeps the condition, location, lot and researched price, so an ended listing or a mis-click can be undone. **`GET /inventory` reads the shared comp snapshots and must never research** (see the `ebay-api-rate-limits` skill): a pile can hold hundreds of distinct cards, so a page load that priced them would fire hundreds of Browse calls. Pricing is therefore a separate, deliberate action that goes through `POST /valuation/batch` — already capped at `MAX_BATCH` — and writes nothing to the inventory row: it refreshes the *shared* `active_price_snapshots`, and the next `GET /inventory` picks the number up. The page spends a call per card you add (one card, one lookup, as the Valuation page does) and offers a counted button for the backlog; nothing prices itself on load. A row's `card_query` is either a catalog identity or, when it carries no `set_name`/`number`, the free-text words of an eBay search — the same two-way split the Valuation page makes, and what lets an off-catalog row be priced at all (`browse_api` truncates any query to `MAX_QUERY_WORDS`, so the UI warns when the typed text is longer). Such a row gets no card art, since nothing in the catalog resolves it. `manual_value` (migration 0012) is a per-unit price stated by hand — for sealed, bulk and anything already appraised, and as an override when a comp pool is visibly wrong for a printing. It **wins over comps** and the condition multiplier is deliberately **not** applied to it, the same rule `/valuation/manual` follows: a comp average is a mixed-condition figure that must be scaled to the card in hand, but a price the seller typed already *is* that card's value, so scaling it again would quietly reduce a number they stated outright. Such a row reports `value_status: 'manual'` so the page can say whose number it is, and it is skipped by the bulk-pricing button. The bulk endpoints (`bulk-update`, `bulk-delete`) are scoped by `user_id` in the WHERE, so ids that aren't yours simply don't come back and the returned count is what actually changed. `bulk-update` writes only the fields the request *sent* — it reads `model_fields_set`, so an absent key means leave the column alone and an explicit null means clear it, a distinction a plain `None` default cannot express. Its column names come from `_BULK_COLUMNS`, never from the request. Both the read and the write degrade if 0012 hasn't been run: rows still load and save, and only a supplied manual value is refused. A row with no cached snapshot reports `value_status` rather than a zero, and a snapshot with no `pool_quality` is flagged `unfiltered` because it predates comp filtering. The number shown is one cached average times the shared condition multiplier — it is **not** a suggested price and must not grow guardrails or staleness blending. Sorting is otherwise done in SQL (`_SORT_COLS`), but the list's **default sort, card type**, is the one exception — there is no `type` column, so `SORT_TYPE_KEY` bypasses `_SORT_COLS` entirely and `_sort_by_type` re-sorts the already-fetched, unpaginated items in Python, using `cards.card_type_label()` (an elemental type like "Fire"/"Grass" for a Pokemon, or the supertype itself for a Trainer/Energy card) resolved once per distinct `card_query` the same way `_card_images` resolves art. This is only exact because the whole pile comes back in one response with no pagination to break across; Value stays unsortable for the same underlying reason (computed post-query) but isn't given the same treatment, since it's a number rather than a handful of buckets. `card_type_label` needs the local catalog cache's `types` field (added alongside `supertype`/`subtypes` in `cards.py`'s `_build_cache()`), so a cache built before that field existed sorts every Pokemon into the "unknown" bucket until `CACHE_MAX_AGE_DAYS` triggers a refresh.
- **The listing CSV is where an inventory row leaves the app.** `POST /inventory/listing-csv` takes ids and a `mode`, and turns those rows into one of eBay's two bulk-upload files, built in `services/listing_csv.py`. **`draft` (the default) writes the draft-listing template** — `Action=Draft`, rows land in ebay.com/sh/lst/drafts to be finished in the listing tool — and it carries **no business-policy columns at all**, so it is the one export with no Settings prerequisite and the way round a policy name eBay won't resolve. **`add` writes the File Exchange template**, which creates listings outright and does need all four Settings fields. The two use different spellings of the same ideas (`Custom label (SKU)` vs `CustomLabel`, `Category ID` vs `*Category`, `Price` vs `*StartPrice`, no leading stars), which is why both column lists are written out rather than derived from each other. Rows are decided identically either way — same title, same price, same floor. **Both need a photo**: eBay rejects a photoless listing outright (21919136), so `PicURL` / `Item photo URL` carries `inventory.photo_urls` and a row without one is warned about rather than skipped, since the fix is a photo on the row, not a smaller selection. — pure, no DB and no network, given rows and their cached snapshots the way `inventory_value` is. It **never researches**, for the same reason `GET /inventory` doesn't: an unpriced row is reported as skipped rather than listed at a guess, alongside sealed/bulk rows, which have no `card_query` and so would land in the wrong category. Its `*StartPrice` is **not** the suggested-price model — that model repositions a *live* listing and needs the current price, days sat, search rank and watchers, none of which an unlisted card has — it is the same condition-adjusted comp average the page already shows, clamped by `net_floor` and snapped by `psych_round` (floor first, round up on a retry, the ordering `compute_suggested_price` uses). `CustomLabel` carries the row's lot SKU, because `routers/lots.py` groups every order and listing by exactly that string. Three omissions are deliberate and must stay: **no ad rate** (a rate baked into a fifty-row upload is the automatic ad spend the `auto_boost_promotion` removal exists to prevent), **no Best Offer** (thresholds are the seller's, same rule as `revise_best_offer_thresholds`), and **no graded cards** (every price descends from a comp pool that screens slabs out). The title is capped at 80 characters and trimmed from the least identifying end so the grade abbreviation always survives — `trading_api.resolve_condition` prefers the title over eBay's condition field, so a title that lost its grade would price the card as generic Ungraded. Listing defaults (description, weight, dimensions, format, shipping profile) mirror `ebay-defaults-extension/defaults.js`; that is a second copy, and the `listing-defaults-audit` skill says which fields must be changed in both.
- **There are two routes from an inventory row to a listing, and they are not variants of each other.** The File Exchange CSV above decides everything itself and produces a file that creates listings outright. `services/prefill_template.py` + `POST /inventory/prefill-template` is eBay's **prefill** flow, a three-step round trip where *eBay* suggests the category, title and aspects: this app fills step 1 (SKU, photos, title, category, aspects), the seller uploads it to Seller Hub, eBay returns a file of suggestions, and the seller completes that file there. **Steps 2 and 3 are deliberately not in this app** — the returned file's schema is eBay's and undocumented here, and half-parsing it would be worse than not touching it. The template is **stored and edited in place, never generated**: eBay's instructions say not to change the file's formatting, so the seller keeps their blank template on the Settings page (`listing_defaults.prefill_template`, migration 0017) and `openpyxl` opens a copy of it, writes cells and hands the same file back — every other sheet, style and unrecognised column survives, and rows append below anything typed by hand. Columns are located by **header text, whole-word matched** (`_HEADERS`), never by position: a fixed column letter that shifted would write titles into the category cell, and `title` matched as a substring would claim a `Subtitle` column. A file that isn't the template is a 422 naming what was looked for, including anything `load_workbook` refuses to open — and that check runs at **upload** time (`prefill_template.validate`, shared with `fill` through `_open`), because a template rejected on Settings costs one re-download while one rejected mid-export wastes the selection about to go into it. Title, category and aspects come from `listing_csv` (`identity`, `build_title`, `card_aspects`, `CATEGORY_PATH`) so the two files can never describe the same card differently. `CustomLabel` is the lot SKU here too, and deliberately **not** a unique per-row key even though eBay recommends one for correlation — `routers/lots.py` groups all money by exactly that string, so anything else orphans the listing from its lot; rows correlate by title instead. Unlike the CSV, an **unpriced row is perfectly listable**: the prefill file carries no price at all.
- `inventory.photo_urls` (migration 0016) is the only place photos are stored — up to 24 `https://` links separated by a pipe, first one first, which is eBay's own format and the order it reads to identify the item. Validated on save (`_clean_photos`), because a link rejected then costs one correction while one rejected after a prefill upload costs the whole round trip. It is **not** `card_image_url`, which is catalog art of the printing resolved at read time: that can't show a condition, and eBay's terms make the seller warrant rights to every URL supplied.
- The inventory write path builds its INSERT/UPDATE from `existing_columns` rather than from hand-written fallback statements (`_WRITE_COLUMNS` + `_OPTIONAL_WRITE_COLUMNS`). Two optional columns already needed four statements and the next migration doubles it again — the same reasoning `_select_for` uses for reads. A value supplied for a column the database lacks is refused with that column's migration hint, never silently dropped.
- `routers/settings.py` + `services/listing_settings.py` — the four things the CSV needs that an inventory row cannot know: the item location and the exact Seller Hub names of the shipping, payment and return policies (`listing_defaults`, migration 0015, one row per user). They are on **Settings**, not in the export dialog and not in `localStorage`, because they are identical on every export forever and because a policy name that doesn't match Seller Hub is the commonest cause of a rejected upload — so getting it right once should hold on every machine the user signs in from. All four are required: `listing_csv_for_items` refuses with a 400 naming the gaps rather than guessing, since a guessed policy name doesn't produce a slightly-wrong listing, it produces a rejected file. `shipping_profile` is the one field with a default, because it has to stay a `SHIPPING_PRICE_MAP` key or the CSV's price floor assumes postage is free. eBay's blank prefill template lives on the same row but deliberately **not** in `FIELDS` — that SELECT runs on the listing-CSV path, which has no use for a workbook and should not drag bytea through a five-connection pool; `template_meta` reports name, date and `length()` without fetching the bytes, and `load_template` is the only thing that reads them. `save_template` is its own upsert rather than a branch of `save`, or saving a policy name would wipe the file. `PUT` accepts a partial save — half-filled is a normal state on the way to filled, and refusing it would lose the two fields you had already looked up. Both the read and the CSV degrade if 0015 hasn't been run. A fifth, optional field lives on the same row: `min_price` (migration 0018) is a seller-set floor the Listing CSV's starting price is never allowed under, on top of `net_floor`'s fee/postage floor — `listing_csv._effective_floor` combines the two, and `_draft`'s warning text says which one actually raised a given row's price. Unlike the four required fields it never gates the CSV (`missing()` doesn't mention it) and degrades the same way `manual_value`/`photo_urls` do on the inventory table: a value supplied when 0018 hasn't been run is refused rather than silently dropped, but the four required fields still save fine either way. Saving a non-null `min_price` also runs `inventory_value.raise_below_minimum` against the existing pile — see that entry above.
- `routers/lots.py` — buying lots, grouped by the SKU already stamped on listings and orders (`L0030`, `L0041`, …). `PULL`, `NONTCG` and rows with no SKU aren't purchased lots and are excluded (`EXCLUDED_SKUS`) — but the filter is applied *after* the per-line allocation below, never before, or a mixed order's whole net lands on the one real lot in it. Only the user-entered fields are stored (`lots`, migration 0008: title, cost, purchase date, source, notes — `title` came later in 0009, so both the read and the write degrade if that hasn't been run: costs still save and only a supplied title is refused). Units sold, net proceeds, live items and listed value are aggregated on read. **eBay puts order-level money on only one row of a multi-item order**, so `SUM(order_earnings)` grouped by SKU credits a whole mixed order to one lot and gives the others zero — the query instead splits each order's net across its lines by their share of order item value, which conserves exactly. Any new per-SKU or per-card money aggregate has the same trap. Unlisted stock (`inventory` rows with the lot's SKU) is rolled up per lot as `unlisted_items` / `unlisted_value` — counted apart from `active_items` because nobody can buy it, and included in `projected_profit` (`sold_net + listed_value + unlisted_value − cost`) — optimistic on two counts, which is the point of the name: no fees come off the unsold half, and the unlisted part is not even on eBay yet, so its value is what the market *asks* for that card rather than a price anyone agreed to pay. Unpriced unlisted rows contribute nothing, so such a lot is understated rather than guessed at. A SKU that only inventory knows about still appears as a lot, since cataloguing a lot before listing any of it is the normal order of events. `GET /lots/{sku}` drills into one lot's sold and active listings and shares that allocation through `_SOLD_LINES_CTE`, so a sold line shows its allocated share of its order's net and the rows still sum to the figure the list page shows.
- `services/ebay_client.py`, `ebay_oauth.py` — per-user eBay OAuth (PKCE). Refresh tokens are Fernet-encrypted at rest (`EBAY_TOKEN_ENCRYPTION_KEY`).
- SQL is Postgres-flavored (the migration off SQLite is done at the DB layer); don't reintroduce SQLite-specific syntax (`?` params, `CAST(x AS REAL)`, `strftime`) in new queries — see the mapping rules in `docs/SOFTWARE_PLAN.md` §6.3 if porting old SQL.

React 19 + TypeScript + Vite, served by FastAPI in prod. Route map, shared

the frontend" rule are in `dashboard/frontend/CLAUDE.md`, which loads when you work

## Working across the pipeline/dashboard boundary

Pipeline scripts write to Excel + local SQLite; the dashboard reads Postgres and re-syncs from Excel on each startup/trigger. If you change a column name or add a field in the Excel sheets (`get_active.py`, `append_sold_orders.py`), you must also update the corresponding column-mapping dict in `dashboard/backend/services/excel_sync.py` (`_SOLD_COLUMNS`, `_ACTIVE_COLUMNS`) or the new field silently won't reach the dashboard.

Similarly, a field added to the Excel path usually needs adding to the OAuth path (`services/ebay_data.py`) too, or connected users won't get it.
